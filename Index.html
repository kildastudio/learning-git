Repository (repo)

What it does

A repository is the project folder tracked by Git. It holds your code, its full history, and configuration. When hosted on GitHub (or GitLab, Bitbucket), it becomes the shared source of truth for your team.

Considerations

  • Initialize with git init locally, or create one on GitHub first.
  • Never commit secrets — use .gitignore for env files and credentials.
  • Keep repos focused: one project per repo is easier to manage.
  • README files help collaborators understand setup and purpose.

Resources

  • Git Book — Getting a Repository
  • GitHub Docs — Repositories
  • gitignore templates

Clone

What it does

Cloning downloads a complete copy of a remote repository — including all branches and commit history — to your local machine. It's how you start working on an existing project.

Considerations

  • Use git clone <url> with HTTPS or SSH URLs.
  • SSH keys avoid repeated password prompts on GitHub.
  • Clone once; use pull to stay up to date afterward.
  • Large repos can take time — consider shallow clones (--depth 1) for CI.

Branch

What it does

A branch is a safe parallel timeline of your codebase. You can experiment, build features, or fix bugs without affecting the main line of development until you're ready to merge.

Considerations

  • Name branches descriptively: feature/login-page, fix/nav-bug.
  • Keep branches short-lived — merge or delete when done.
  • main (or master) should stay deployable.
  • Use git checkout -b name or git switch -c name to create one.

Resources

  • Git Book — Branching
  • Atlassian — Using branches
  • Git Flow model

Commit

What it does

A commit is a snapshot of your project at a point in time, paired with a message describing what changed. Commits form the history you can browse, revert, or compare.

Considerations

  • Write clear messages: imperative mood, e.g. "Add login form validation".
  • Commit often, in small logical chunks — easier to review and revert.
  • Stage with git add, then commit with git commit -m "message".
  • Each commit should represent one coherent change.

Resources

  • How to Write a Git Commit Message
  • Conventional Commits

Push / Pull

What it does

Push uploads your local commits to the remote repository. Pull downloads new commits from the remote and merges them into your current branch. Together they keep local and remote in sync.

Considerations

  • Always pull before you push to avoid conflicts.
  • git push -u origin branch-name sets upstream tracking.
  • Never force-push to shared branches unless the team agrees.
  • git fetch downloads without merging — useful to preview changes.

Resources

  • git push docs
  • git pull docs
  • GitHub — Pushing commits

Diff

What it does

A diff shows the visual difference between two versions of code — lines added, removed, or changed. It's essential for code review, debugging, and understanding what changed between branches or commits.

Considerations

  • git diff compares working directory vs. staged; git diff --staged vs. last commit.
  • git diff main..feature compares two branches.
  • IDEs and GitHub render diffs with color — green for additions, red for deletions.
  • Review diffs before committing to catch accidental changes.

Merge

What it does

Merging combines the changes from one branch into another. When you finish a feature branch, you merge it back into main so everyone gets your work.

Considerations

  • Switch to the target branch first: git checkout main && git merge feature.
  • Fast-forward merges happen when there's no divergence — clean and simple.
  • Merge commits appear when histories diverged — that's normal.
  • Resolve any conflicts before the merge completes.

Rebase

What it does

Rebasing replays your commits on top of the latest main, creating a linear history. Instead of a merge commit, your changes appear as if you started from the most recent main.

Considerations

  • Never rebase commits that have already been pushed and shared.
  • Great for cleaning up local feature branches before opening a PR.
  • git rebase main while on your feature branch.
  • Conflicts can occur at each replayed commit — resolve them one by one.

Resources

Merge Conflict

What it does

A merge conflict happens when two changes touch the same lines of code and Git can't decide which version to keep. Git pauses the merge and marks the file — you choose the correct result.

Considerations

  • Look for <<<<<<<, =======, and >>>>>>> markers in the file.
  • Communicate with teammates when conflicts involve shared files.
  • After resolving, git add the file and continue the merge/rebase.
  • Pull frequently to reduce the chance of large conflicts.

  • GitHub — About merge conflicts

Pull Request (PR)

What it does

A pull request is a request to merge your branch into another (usually main). It opens a space for code review, discussion, automated tests, and approval before changes land.

Considerations

  • Keep PRs small and focused — easier to review and less risky.
  • Write a clear title and description explaining the "why".
  • Link related issues with "Closes #123" to auto-close them.
  • Respond to review feedback promptly and push updates to the same branch.

Resources

  • GitHub — About pull requests
  • GitHub Code Review
  • Atlassian — Making a pull request

Issue

What it does

An issue is a ticket for tracking bugs, feature requests, or tasks. Issues live in the repository and can be assigned, labeled, linked to PRs, and organized on project boards.

Considerations

  • Use labels (bug, enhancement, docs) for filtering and triage.
  • One issue per problem — avoid bundling unrelated work.
  • Reference issues in commits and PRs to create traceability.
  • Templates help contributors provide the right information upfront.
